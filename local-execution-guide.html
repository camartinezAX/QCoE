⚙️ First-Time Setup

Clone & install dependencies

terminal
$ git clone <repo-url> && cd Axos.Auto_Mobile
$ npm install

Set ANDROID_HOME Android

Appium needs this to find SDK tools. Skip if already set.

~/.zshrc
export ANDROID_HOME=$HOME/Library/Android/sdk
export PATH=$ANDROID_HOME/platform-tools:$PATH

Then run source ~/.zshrc or open a new terminal.

PowerShell
# Set ANDROID_HOME and ANDROID_SDK_ROOT permanently (typical path)
$sdk = "$env:LOCALAPPDATA\Android\Sdk"
> setx ANDROID_HOME $sdk
> setx ANDROID_SDK_ROOT $sdk
> setx PATH "$env:PATH;$sdk\platform-tools"
⚠️
CRITICAL: After running setx commands, you must fully restart Cursor (not just the terminal). Environment variables set with setx only take effect in new processes.

Verify after restart with adb --version and echo $env:ANDROID_HOME.

Install the Axos app on your device

The app must be installed on the device before running tests (when using USE_INSTALLED_APP=true).

PlatformWhere to download
Android Firebase (internal builds — UAT, QA, STG)
Google Play Store (prod)
iOS Firebase (internal builds — UAT, QA, STG)
Apple App Store (prod)
💡
For prod testing, simply download the public app from the Play Store / App Store, set TEST_ENV=prod in .env, and you’re good to go. For internal environments (UAT, QA), get the build from Firebase.

Set these before running any tests:

🔌 iOS Device & Xcode Setup

Add an Apple Account in Xcode

You need an Apple ID signed into Xcode to code-sign WebDriverAgent. Any personal Apple ID works — it does not have to be an Axos account or a paid developer account.

  1. Open Xcode → Settings (or ⌘,)
  2. Go to the Accounts tab
  3. Click the + button (bottom-left) → Apple ID
  4. Sign in with your Apple ID (personal is fine)
  5. Once added, note the Team ID shown under your account — you’ll need it for WDA setup
💡
Free Apple IDs generate provisioning profiles that expire every ~7 days. The framework handles this automatically — see the note below about the auto-rebuild & trust cycle.

Enable Developer Mode (iOS 16+)

On the device: Settings → Privacy & Security → Developer Mode → toggle ON. The device will restart.

⚠️
Without Developer Mode, Appium cannot install or launch apps on the device.

🔄
Every ~7 days: Trust the Developer Certificate

Free Apple Developer provisioning profiles expire approximately every 7 days. When this happens, the framework automatically rebuilds WebDriverAgent with a fresh profile and installs it on your device. Because it’s a newly signed app, iOS will block it until you trust the developer certificate again.

The framework detects this and stops the test run with a clear message telling you exactly what to do:

  1. On your iPhone: Settings → General → VPN & Device Management
  2. Tap your Apple Development certificate
  3. Tap “Trust” and confirm
  4. Re-run your tests — they will start normally

This is a normal part of iOS development with free Apple IDs. No action is needed until the framework tells you.

WebDriverAgent (WDA) One-Time Setup iOS 17+ Required
💡
Why? Appium uses WDA (WebDriverAgent) to control iOS devices. WDA must be pre-built and code-signed with your Apple Developer account. The framework uses xcodebuild to install and launch WDA on every test run automatically.
✅
Auto-rebuild: The framework automatically checks your WDA provisioning profile before every run. If it’s expired or about to expire (free profiles last ~7 days), WDA is rebuilt automatically — no manual steps needed after initial setup. After a rebuild, the framework stops and prompts you to trust the developer certificate on your device before continuing.

Prerequisites

  • Xcode installed (version ≥ device iOS version)
  • Apple Developer account added to Xcode (free Apple ID works)
  • Developer Mode ON & device visible in Xcode

Build WDA (one-time)

terminal
TEAM_ID="YOUR_TEAM_ID"
WDA_BUNDLE="com.yourname.wda.runner"
DERIVED="/Users/$USER/DerivedData/WDA"
WDA_PROJECT="$(find node_modules/appium-xcuitest-driver -name WebDriverAgent.xcodeproj -maxdepth 5 | head -1)"

$ xcodebuild build-for-testing \
    -project "$WDA_PROJECT" -scheme WebDriverAgentRunner \
    -destination "generic/platform=iOS" -derivedDataPath "$DERIVED" \
    -allowProvisioningUpdates \
    DEVELOPMENT_TEAM="$TEAM_ID" CODE_SIGN_IDENTITY="Apple Development" \
    PRODUCT_BUNDLE_IDENTIFIER="$WDA_BUNDLE" CODE_SIGNING_ALLOWED=YES

If the device asks to trust the developer certificate: Settings → General → VPN & Device Management.

When to redo?

  • Free profile expired (7 days): Handled automatically — the framework rebuilds WDA on the next test run
  • New device (same account): Update .env with new UDID — WDA is installed automatically
  • Different Apple account: Rebuild WDA with the new Team ID
  • Appium driver update: Rebuild WDA (use the AI prompt below)
  • Normal daily runs: Nothing — just plug in and go

⚙️ How It Works
Execution Flow

When you run with a GREP tag, here's the exact flow:

GREP filter
→
Load matching specs
→
Start Appium
→
Create session
Run test 1
→
afterTest: reload
→
Run test 2
→
afterTest: reload
→
Done
💡
Two layers of GREP filtering:
Layer 1 (spec files): The shared config scans all spec file contents for the GREP pattern — only matching files are loaded.
Layer 2 (test titles): Mocha's grep option filters individual it() titles — only matching tests execute.
Fresh App Guarantee

After every single test (pass or fail), the local afterTest hook calls browser.reloadSession(). This:

  • Terminates the current Appium session (kills the app)
  • Creates a brand new session with noReset: false
  • Clears app data (Android: pm clear, iOS: sandbox wipe)
  • Launches the app from the very beginning (sign-in screen)
✔️
Every test — and every retry — always starts from scratch. No leaked state.
Retry Behavior (RETRIES in .env)
Test runs
→
FAIL
→
screenshot + reload
→
Retry 1 (fresh app)
→
PASS = flaky
ScenarioWhat HappensAllure Label
Pass on 1st attempt Session reloads for next test passed
Fail, retry passes App restarts, retry runs on fresh state flaky
Fail, retry also fails Marked as failed, moves to next test failed
📌
Key: Only the specific failed it() is retried — not the entire file.
Config: RETRIES=1 in .env → each test gets 1 retry on failure.
Change it: Set RETRIES=2 for 2 retries, RETRIES=0 for none.

Where do reports live?
allure-results/ — raw JSON data (auto-cleaned on each run by onPrepare). Each run wipes the previous results so your report only shows the latest execution.
allure-report/ — generated HTML (created by allure:generate)
✔️
No stale data: Both the Android and iOS configs auto-clean allure-results/ before each run, and write platform-specific environment metadata (device name, OS version, platform). You'll never see leftover Android results in an iOS report or vice-versa.

  • Full error stack traces

Environment metadata

  • Platform (Android / iOS)
  • Device name & OS version
  • Build name & timestamp
  • Test environment (UAT, QA, etc.)
  • Retry setting value

📦 Sharing Reports with Your Team

Allure reports use JavaScript to load data, so double-clicking index.html won't work — browsers block file:// fetch requests. You need to either zip and share, or serve it locally.

Step 1 — Generate & zip (sender)

terminal
# Generate the report from the latest run
$ npm run allure:generate

# Zip the report folder (timestamped so each zip is unique)
$ zip -r "allure-report_$(date +%Y-%m-%d_%H%M%S).zip" allure-report/

Creates a file like allure-report_2026-02-11_143052.zip in the project root. Send it via Slack, email, Teams, etc.

⚠️
Do this before your next test run. Each run wipes allure-results/, so if you don’t generate + zip first, the previous report is gone.

Step 2 — View it (receiver)

Unzip the file, then serve it with a local web server (one command):

terminal
# Unzip (use the actual filename you received)
$ unzip allure-report_2026-02-11_143052.zip

# Serve it (Python is pre-installed on macOS)
$ cd allure-report && python3 -m http.server 8080

# Open in browser
$ open http://localhost:8080
PowerShell
# Unzip (PowerShell)
> Expand-Archive allure-report_2026-02-11_143052.zip -DestinationPath allure-report

# Serve it (Python or npx — use whichever is available)
> cd allure-report; python -m http.server 8080

# OR if Python is not installed:
> npx serve allure-report

# Then open http://localhost:8080 in your browser
💡
Why can't I just open index.html? Allure loads test data via JavaScript fetch() calls. Browsers block these on file:// URLs for security reasons. A tiny local web server (python3 -m http.server) serves the files over http://localhost, which browsers allow.
📌
If the receiver has Node.js but not Python, npx serve allure-report works just as well (no install needed, npx downloads it on the fly).

Troubleshooting

Common issues & fixes
🤖
Easiest fix? Copy the error message, paste it into Cursor, and ask the AI to help. It already knows this project's setup and can usually solve it in seconds.

💥 Common Issues — All Platforms

Appium server fails to start on port 4723

Another Appium instance is already running. Kill it:

macOS:

terminal
$ lsof -i :4723
$ kill -9 <PID>

Windows:

PowerShell
> netstat -ano | findstr :4723
> taskkill /PID <PID> /F
No tests run (0 passing)

Your GREP pattern doesn't match any test titles. Tags are case-sensitive: @Sanity_Login is not @sanity_login.

reloadSession keeps failing

Usually the device disconnected or the app crashed hard. Check USB. The error is caught and logged — the next test will try to create a fresh session anyway.

🤖 Android Issues

"device not found" or "unauthorized"

Ensure USB debugging is enabled and you've tapped "Allow" on the device. Try:

terminal
$ adb kill-server && adb start-server && adb devices
UiAutomator2 signature mismatch

Appium's helper app on the device was installed by a different machine with a different signing key. Fix:

terminal
$ adb uninstall io.appium.uiautomator2.server
$ adb uninstall io.appium.uiautomator2.server.test
# Then re-run your test — Appium will reinstall them
ANDROID_HOME not set (Appium can't find SDK)

Appium needs ANDROID_HOME to locate SDK tools. See the Prerequisites section for setup instructions for your OS.

🏳️ Windows-Specific Issues

GREP="..." npm run doesn't work

GREP="@Tag" npm run test:android is Bash/Unix syntax. It will silently fail or error in PowerShell and CMD.

Fix: Always use cross-env on Windows:

PowerShell / CMD
> npx cross-env GREP=@Sanity_Login npm run test:android

Or use the built-in scripts that already use cross-env: npm run test:android:sanity

adb: "not recognized as a command"

adb is not in your system PATH. Either:

  • Use the full path: %LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe
  • Or add platform-tools to your PATH permanently (see Prerequisites)
JDK or Android SDK installation fails (network/proxy error)

Corporate machines often block winget, choco, or direct downloads due to proxy/firewall policies. Do not try to bypass these restrictions.

Fix: Submit a single ServiceNow Software Request for Java JDK 11+ and Android Studio. Select OTHER and Yes in the form. See the Prerequisites → First-Time Setup section for exact copy-paste text.

After IT installs them, restart Cursor and re-run the setup AI prompt.

npm install fails or node_modules missing

Make sure you run npm install in the project root before anything else. This installs Appium, WebDriverIO, cross-env, and all dependencies.

"ANDROID_HOME not set" even after running setx

The setx command sets environment variables permanently, but they only take effect in new processes. The terminal you're currently using still has the old environment.

Fix: You must fully restart Cursor (close it completely and reopen). Reopening just the terminal is not enough.

After restarting, verify:

PowerShell
> echo $env:ANDROID_HOME
# Should show your SDK path, e.g. C:\Users\YourName\AppData\Local\Android\Sdk
Appium timeout: "uiautomator2ServerInstallTimeout"

The first time Appium runs on a device, it installs UIAutomator2 server packages. This can take >20 seconds on some devices.

The config already has increased timeouts (uiautomator2ServerInstallTimeout: 120000). If you still see this error:

  • Uninstall old packages: adb uninstall io.appium.uiautomator2.server and io.appium.uiautomator2.server.test
  • Make sure the device screen is unlocked
  • Try a USB 3.0 port for faster transfer
Port 4723 already in use

Another Appium server (or a previous stuck process) is using the port. Kill it:

PowerShell
> taskkill /F /IM node.exe /T
# This kills all Node processes. If you have other Node apps, find the specific PID instead.

🍎 iOS Issues Mac Only

xcrun xctrace list devices crashes

Intermittent Xcode bug. Two fixes:

Fix 1: Warm up Xcode's device service, then retry:

terminal
$ xcrun devicectl list devices   # may hang — Ctrl+C after 5s
$ xcrun xctrace list devices     # should work now

Fix 2: Use idevice_id instead: brew install libimobiledevice && idevice_id -l

WDA build fails (code signing error)

Make sure your Apple Developer account is added to Xcode, the device is registered, and xcodeOrgId in wdio.ios.conf.js matches your Team ID. Use the Full WDA Setup AI prompt in the Device Setup section.

WDA session times out / tests never start

If the auto-rebuild did not fix it, try a manual rebuild:

terminal
# Delete old build and rebuild fresh
$ rm -rf ~/DerivedData/WDA
$ GREP="@Sanity_Login" npm run test:ios  # auto-rebuild triggers on next run

If that still fails, use the Full WDA Setup AI prompt.

"Automation Running — Hold both volume buttons to stop"

This is completely normal. WDA launched successfully. Do not press the volume buttons.

Free Apple ID provisioning profile expired

Free profiles expire every 7 days. This is now handled automatically — the framework detects expired profiles and rebuilds WDA before tests run (see tools/ensure-wda.js). Just run your tests normally and the rebuild happens in the background. You’ll see [ensure-wda] log messages showing the auto-rebuild.
