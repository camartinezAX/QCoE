QE Standard Runbook — Azure DevOps (ADO)

Audience: QE Engineers, QE Leads, QE Managers, Dev, SDMs, Vendors Purpose: Establish a single, clear, enforceable standard for how Quality Engineering uses Azure DevOps (ADO). Goal: Remove ambiguity, reduce noise, improve triage speed, and ensure consistent QE signaling.

1. Scope and Principles

What this runbook is

  • A practical execution guide for QE usage of ADO
  • A source of truth for states, tags, approvals, and ownership

What this runbook is NOT

  • Not a tutorial on ADO features
  • Not a replacement for product or scrum processes

Guiding principles

  • Consistency over flexibility
  • Signal over noise
  • QE owns quality signals, not delivery dates

2. Work Item Types QE Uses

Product Backlog Item (PBI)

  • Owned by Product / Dev
  • QE does not create or rewrite PBIs
  • QE validates acceptance criteria against PBIs

Bug

  • Created by QE when behavior deviates from acceptance criteria or expected system behavior
  • All QE-found defects must be logged as Bugs, not comments
  • Bugs must be linked to a parent PBI, feature, or release item

QE Task

  • Used only when explicitly required by team agreements
  • Must always be linked to a PBI
  • Should represent QE effort (design, execution, regression, automation)

3. QE-Owned States and Transitions

QE touches ONLY these states

  • Ready for Test (RFT)
  • QA Approved
  • Rejected by QA
  • QA Blocked

General state rules

  • QE does not move items into Dev Ready, Resolved, or Done
  • QE state changes must reflect actual validation status, not intent

QA Approved means

  • Acceptance criteria validated
  • Evidence documented
  • Required automation expectations met or explicitly waived

Rejected by QA

  • Used when validation fails or fix is incomplete
  • Item must be triaged
  • Dev is responsible for fixing and moving the item forward
  • QE re-tests only after Dev updates the item appropriately

Anti-patterns (Not allowed)

  • Using comments instead of state changes
  • Marking QA Approved with missing evidence
  • Advancing state to unblock development without validation

3.1 Release Regression Bug — Required State Flow

This section applies only to release regression bugs.

Definition

A Release Regression Bug is a defect found during release validation or regression testing that impacts existing, previously working functionality.

Required state flow

New

  • Bug created by QE with a clear regression context
  • Mandatory regression tags applied

Ready for Test (RFT)

API & Web
  • Dev moves the bug/work item to the Build Complete state and shares the build artifacts with QA
  • Release Managers deploy the fix to the Main environment
  • QE sets the state to Ready for Test only after successful deployment
Mobile
  • Dev owns deployment
  • Dev sets the state to Ready for Test only and build versions are tagged to the work item or bugs
  • QE must not pull bugs into test before deployment

4. Tagging Standards

Mandatory tagging rules

  • Tags are signals, not documentation
  • Use only approved tags
  • No custom / ad-hoc tags

Required tag examples (adjust per org standards)

  • CreatedBy_QE, Conditional_QA_Approved, etc.
  • ReleaseRegressionTags — e.g. OLB145Release
  • Release identifiers (only if officially defined)

Release Regression tagging rules

All release regression bugs must include:

  • ReleaseRegressionTags
  • Tags must be applied at bug creation
  • Tags must not be removed during the lifecycle of the bug

Forbidden practices

  • Multiple tags with the same meaning
  • QE-specific logic encoded inside tags
  • Tags used to replace comments, repro steps, or evidence

5. QE Approval Criteria

A work item can be marked QA Approved only when all are true:

  • Acceptance criteria verified
  • Test scenarios (positive + negative) executed
  • Environment documented
  • Evidence attached (screenshots, logs, recordings)
  • Automation expectations met or explicitly approved for exception

QA Approved is a quality signal, not a scheduling or release signal.

6. Bug Management Expectations

Bug creation standards

  • Clear, concise title
  • Steps to reproduce
  • Expected vs actual behavior
  • Evidence attached
  • Correct parent linkage
  • Regression context explicitly stated when applicable

Bug ownership

QE Owns bug quality and clarity
Dev Owns fix and deployment
Re-validation QE re-validates only after Dev moves the item to Ready for Test

7. Escalation and Ownership

First point of contact

QE Leads for clarification and unblock.

When to escalate

  • Blocking test execution
  • Invalid rejection or premature state changes
  • Repeated process or state violations

Not an escalation

  • Priority disagreements
  • Delivery timeline concerns

8. Common Anti-Patterns (Do NOT Do This)

  • Comments instead of bugs
  • Custom tags
  • QA Approved without evidence
  • Pulling bugs into test before deployment
  • Waiting silently when blocked
  • Using ADO to solve communication gaps

9. Enforcement

  • This runbook applies to all QE work in ADO
  • Deviations must be explicitly approved by QE Leadership
  • Repeated violations may result in items being sent back without validation
  • Updates to this runbook are controlled and versioned
